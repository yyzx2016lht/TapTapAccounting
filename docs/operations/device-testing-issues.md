## 三、核心架构演进方案：待记流水与功能收敛至敲敲记账主应用

### 1. 演进背景与为什么必须收敛
原设计选择“插件持有收件箱（B3 方案）”的理由（单独升级、供外部记账 App 复用）在实际开发与自用场景下已不成立。相反，双 App 架构在真机实测中暴露出一系列难以逾越的系统级硬伤：
- **后台冻结与进程查杀（ISSUE-06）**：国产系统对独立插件进程冻结极快，主应用拉取数据频频报 `Failed to find provider info`；
- **后台启动 Activity 拦截（ISSUE-10）**：Android 10+ 后台启动限制（BAL）导致跨应用调起相册直接失效；
- **双悬浮窗打架与入口脱节（ISSUE-08）**：插件与主应用各搞一套 WindowManager，界面撕裂；
- **拆分记账协议脆弱（ISSUE-05）**：跨进程传输多笔拆分与图片明细流程长且极易丢失。

### 2. 目标架构与核心工程原则（职责分明）
1. **插件必须保留为独立的小 APK（绝不把 Hook 塞进主应用）**：
   - 敲敲记账主应用需要面向应用商店发布（包含 `store-assets/`），主应用内严禁包含 Xposed/LSPosed 模块声明与 Hook 代码，否则会面临严重的安全合规风险与审核封禁；
   - 插件仅保留为极简的 Hook 转发小模块，主应用保持完全合规干净，无 Root 用户零感知。
2. **底层报文解析保留在插件内部**：
   - 微信/支付宝的底层 XML、Hook 逻辑与原始报文解析依然在插件中完成，插件将其结构化为通用的 `CaptureContract` 标准数据对象；
   - 当微信/支付宝升级改版时，只需单独更新几十 KB 的轻量插件，敲敲记账主应用无需频繁更新发版。
3. **跨进程投递与本地暂存兜底机制**：
   - 支付发生时，微信/支付宝位于前台，通过广播/IPC 向敲敲记账投递账单，通常能顺利唤醒；
   - **可靠性兜底**：若主应用当时无响应或被系统极端强杀，插件侧在轻量本地暂存该条账单，待主应用活跃时重试投递，杜绝漏单；
   - 针对 Android 12+/14/15 的后台启动前台服务（FGS）与悬浮窗（BAL）限制，在真机上严密压测投递唤醒通道。
4. **业务缺陷先修，无需等待大重构**：
   - 像 ISSUE-10（PhotoPicker 前台直接调起）、ISSUE-04（规则学习条件放宽）、ISSUE-02/03（分类覆盖逻辑）属于局部纯业务 bug，立即在当前分支优先修复，立竿见影。

### 3. 用户体验与入口层级设计
- **无 Root 普通用户视角**：
  - 主界面 100% 清爽干净，完全不显示“待记 0 笔”或任何 Xposed 相关选项；
  - 仅当用户手动“稍后记”或从外部导入了临时账单时，首页资产卡片上方才轻盈浮现一个微型胶囊条；记完后自动彻底隐藏。
- **有 Root / 自动记账用户视角**：
  - **现场秒记（屏幕全局悬浮窗）**：付完款瞬间主应用秒弹悬浮窗，顶部细条展示金额，原地支持改备注、拆分多笔明细卡片、拍照识别小票，一键合并入账；
  - **事后集中处理（主应用首页）**：若现场划掉，打开 App 首页顶部显示 `📌 有 N 笔待记账单等待入账 [速清]` 动态胶囊，清空后自动平滑收起。
